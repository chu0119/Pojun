# 模型路由策略（v0.3.95 B11）

> 配置面早已就绪：goals / planner / worker / mainagent / judge / compactor 六个角色
> 各有独立 LLM 解析（Agent 绑定 → 任务链 → 全局激活；judge 还有独立 profile+prompt+超时）。
> 本文档落的是**策略与默认建议**——哪个角色该配什么档位的模型、为什么。

## 一、角色 × 模型档位建议

| 角色 | 建议档位 | 理由 |
|---|---|---|
| **planner** | **强推理（thinking）** | 判断型任务：去重、接续归因（stop_reason）、目标判定（prove_goal 量化核对）、深度-广度仲裁。每轮短、system 静态利于缓存——强模型的判断力花在刀刃上 |
| **worker** | **强执行 + 中推理** | 每轮全量工具循环，thinking 会拉长每步延迟并挤占 idle-stop 计数窗口（thinking-only 回合既不写回也不被 nudge 救——nudge 只挂在 Stop）。若用 thinking 模型，run_timeout 必须留裕量 |
| **judge（拦截裁决）** | **非思考 / 低思考** | 180s 超时是硬约束：思考型模型耗时要 32768→65536 升预算重试；裁决质量来自 prompt 结构（双轴判据+对照样例）而非模型深度 |
| **goals（目标拆解）** | **便宜模型** | MaxTurns=8 的结构化抽取任务（set_goals/set_constraints），旗舰模型无收益 |
| **compactor（上下文压缩）** | **便宜、非思考** | 纯摘要任务。此前绑 planner 同模型烧 65536 token + 20 分钟墙钟——压缩调参的全部痛点源于此。v0.3.95 起支持独立配置，默认应降档 |
| **mainagent（人在环路）** | **强推理** | 与 planner 同级判断（steer/kill 前的取证、补意图），交互频次低，质量优先 |

## 二、三通道池的分工建议

三通道轮询（llm_pool）解决**可用性**；角色路由解决**质量与成本**。两者正交：

- 免费通道（`:free` 档 / flash 档）：适合 worker / goals / compactor——量大、单步浅。
- 付费/旗舰通道：优先给 planner 与 mainagent——每轮短、判断密度高，token 花得值。
- judge 建议固定绑一个稳定通道（`llm_judge_profile_id`），裁决路径不要参与池子轮询——
  裁决中途熔断会走 fail_action（默认 ask），扰动审批体验。

## 三、thinking 预算

`MaxTokens` 是思考+正文共用预算。思考型模型配小了会把「模型在思考」误判成
「正文为空」触发升预算重试。v0.3.95 前**没有**独立 thinking 旋钮——配 thinking
模型时 MaxTokens 给足（≥32768），并把超时同步放大。

## 四、不做的事

- **按错误率动态升降模型**：状态复杂、可解释性差；现有「绑定 + 任务链 + 手动切换
  + 审计事件」已覆盖。
- **judge 用 thinking**：见上，超时风险大于收益。

## 五、思考强度（reasoning_effort）与 LLM 配置解耦

强度是**请求参数**，不是模型身份。此前要改一个 Agent 的强度只能复制整份 LLM 配置，
导致同一模型出现多份 profile、限流器与池成员重复。现在分两层：

- `llm_profiles.reasoning_effort`：该配置自身的默认强度（`""` = 不发送）。
- `agent_profile_effort_overrides(agent_key, profile_id, reasoning_effort)`：某 Agent 在
  某配置上的独立强度，不复制配置。

解析顺序固定为 **override → profile → 未设置**，运行时 provider 构造、装配链投影、
路由视图与审计快照共用同一个纯函数（`ResolveEffort`），不存在第二套口径。空 agent key
（pin / judge / 环境变量路径）不读覆盖。覆盖值越出枚举时视为未设置，绝不发送。

生效时机：**下一次模型调用生效**。已经跑起来的会话不会重建 system prompt，也不会把
旧请求的强度改掉；failover 到另一个配置时按**目标配置**重新解析覆盖，不继承来源配置
的值。thinking 降级（收到 2013 后摘掉 `thinking.type` 重试）在配置切换时重置，避免把
降级状态带到新配置上。

provider 缓存按 `(profile_id, 生效强度)` 共享：无覆盖时与直接用该配置**逐字段一致并
命中同一个缓存实例**（同一限流器），有覆盖时才多一个缓存项。注意限流器挂在 provider
实例上，因此**同一配置的不同强度各自拥有一个限流器**，速率不跨强度合计——这是为了
避免不同参数共用一条连接池/限速假设而做的取舍；如需全局速率，应在网关侧限。UI 入口：Agent 编辑器
「思考强度覆盖」区块，与 LLM 配置抽屉的档位选择互不影响；配置抽屉另有反向列表
「被以下 Agent 覆盖」，用于回答「改这份配置会影响谁」。

## 六、额度耗尽的回退链

两层必须分开看：

| 层 | 决定什么 | 何时推进 |
|---|---|---|
| **用户配置链**（任务级 `llm_profile_ids` / Agent 绑定后的池） | 模型身份与顺序 | 仅**额度/余额耗尽**（402、quota、insufficient balance 等） |
| **provider 池**（`llm_pool`） | 同一身份下可用的候选通道 | 健康度/冷却；不改变用户链顺序 |

- **429 限流、超时、5xx、网络错误不推进配置**：先同 provider 重试，必要时摘 thinking
  重试；这些是瞬态，换模型会污染对比与成本。
- 推进按用户配置链顺序，耗尽后停在链尾（不会回绕）；手动切换写入 `manual` 事件。
- 每次推进写一条 activity（`llm_switch` / `llm_failover`），metadata 带
  `llm_transition{agent_key, mode, reason, previous, next}`；只读投影从这张表读历史，
  **不推断**未记录的事件。池内部转移与同 provider 重试不产生该事件——这是已知且
  显式说明的不可观测项。

## 七、只读路由投影 API

`GET /api/agents/{key}/llm-route[?task_id=&limit=&before=]`

- 返回：五层来源优先级（pin → Agent 绑定 → 任务链 → 全局 → 环境）、各角色当前解析、
  任务配置链（游标/状态/最后一次错误，错误文本脱敏）、provider 池（包裹关系、成员
  健康度、是否在链上、是否有 key）、额度转跳规则、运行期转跳历史、最近任务选择器。
- `limit` 是**事件条数**（默认 50、上限 200）；任务选择器固定展示最近 20 个活跃任务。
  无 `task_id` 时历史是跨任务近似视图，不声明精确翻页；`task_id` 指未知或已归档任务
  返回 404，不静默降级为空列表。
- 每层除 `hit` 外，前端按运行时顺序（Agent 绑定 → 任务链 → 全局 → 环境；pin 只钉压缩器）
  标出**实际生效层**；任务有配置链时即使全局可用也不会标全局。
- 静态可用性只有 `ok | missing_key | invalid_config`，表示**配置完整性**，不验证连通性。
- `last_used` 来自常开的 `llm_usage` 记账：该任务 planner / worker / mainagent 三条泳道各自最近
  一条调用（profile_name、model、status、时间）。它回答“刚才实际用的是什么”，**不代表当前游标**；
  记账没有 effort 列，同一配置的不同强度共用 profile_name，因此 effort 无法从该表恢复。
  没有记录时返回空并说明原因，不伪造“默认配置”。
- 该端点只读：不构建 provider、不发请求、不返回凭据；错误文本用正则剔除 Bearer、
  `sk-`、api_key/token 与 URL userinfo 后再截断。

`GET|PUT|DELETE /api/agents/{key}/llm-effort-overrides[/{profile_id}]` 管理覆盖；
PUT body `{"reasoning_effort": "..."}`（空串等同清除），成功 204，DELETE 幂等。
