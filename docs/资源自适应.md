# 资源自适应（容量探测 / 计划 / 作业与扫描闸门）

> 下放自内部版 v0.9.73。公开版默认**关闭**：未开启时 worker 仍按现有设置或默认 3，
> 不限制作业、不缩放扫描、不修改 Go 运行时；升级不会改变任何存量部署的行为。

## 1. 它解决什么

同一份程序会跑在 2C4G 的 VPS、32C64G 的物理机、以及 `mem_limit`/`cpus` 各不相同的
容器里。固定 `workers=3`、固定扫描并发在两种极端上都不合适：小机器被扫描/破解抢满
CPU 与内存，大机器则长期跑不满。资源自适应做三件事：

1. 启动时**只读**探测 CPU、内存、负载、cgroup 限额与数据目录磁盘；
2. 按整机规模分档推导一份保守计划（worker、后台作业并发、扫描速率、Go 堆上限、
   破解器低负载参数）；
3. 用户显式开启后，把计划落到运行期；每小时重算一次，跟上扩容/限额调整。

## 2. 默认策略（零变化）

| 设置 | 默认 | 说明 |
| --- | --- | --- |
| `resource_auto_tune` | `false` | 关闭时只探测并展示，不改变任何运行时行为 |
| `resource_mode` | `auto` | 开启后按容量推导；选 `manual` 时只用下方手工覆盖 |
| `resource_threshold_high` | `85` | 预留阈值，当前只保存（不会主动节流） |
| `resource_threshold_critical` | `95` | 预留阈值，当前只保存（不会主动暂停作业） |
| `resource_auto_pause_scans` | `true` | 同上，仅保存 |
| `resource_manual` | `{}` | 整对象替换；省略字段 = 跟随自动计划 |

关键原则：**只有显式未配置时才用自动值**。

- `workers` 设置在库里存在（老库或用户手动设过）→ 永远以它为准，计划不会覆盖；
- `workers` 从未配置 + 用户开启自动调优 → 才用计划推导值；
- `workers` 显式配置损坏（非数字/<=0）→ 退回默认 3，而不是改吃计划；
- 手工覆盖 `workers` 通过设置页保存时会同时写穿 `workers` 设置（用户显式动作，
  不是静默改写）。

资源设置页的「计划」展示推荐值，「生效」展示实际值，两者不同正是显式配置优先。

## 3. 探测与降级

- Linux：读 `/proc/meminfo`、`/proc/self/cgroup`、`/proc/loadavg`、cgroup v1/v2
  的 `memory.max|memory.limit_in_bytes` 与 `cpu.max|cpu.cfs_quota_us`，对数据目录
  `statfs`（目录不存在时向上找可访问祖先）。
- 容器：`memory.max`/`memory.limit_in_bytes` 与 `cpu.max` 更小时取限额，并标记
  `mem_from_cgroup` / `cpu_from_cgroup`。容器内读不到限额时按宿主值估算，并在
  设置页给出「可能高估，建议设置 mem_limit/cpus」警告。
- 非 Linux：只探测 CPU 核数；内存/磁盘/负载标记为未知，计划按 8G 保守估算并警告。
- 任何单维度失败都只追加 `warnings`，**不阻断启动**，也不写任何系统配置。
- 环境变量 `POJUN_RESOURCE_PROC` / `POJUN_RESOURCE_SYSFS` 可覆盖探测根路径
  （测试/非常规挂载）；`POJUN_RESOURCE_CONTAINER=1` 强制按容器处理。

## 4. 计划档位

| CPU（含配额） | worker | 后台作业全局上限 |
| --- | --- | --- |
| <=2 | 2 | 2（每 worker 一个） |
| <=4 | 3 | 6 |
| <=8 | 4 | 8 |
| <=16 | 6 | 12 |
| >16 | 8 | 12 |

- 内存 <=4G 时 worker 上限压到 2；未探测到内存按 8G 估算。
- 单任务后台作业上限 = `max_jobs/2`（1–6）。
- 扫描速率缩放 = `可用 CPU / 8`，限制在 `0.3–1`；`scan_with_nuclei` 在缩放 <1 时
  自动带 `-rate-limit`（基准 150 req/s，最低 10），手工命令由提示词给出同样参数。
- `GOMEMLIMIT` = 可用内存 55%（512MB–28GB）；`GOMAXPROCS` = CPU 核数向上取整。
- 破解器：>=8 核且 >=16G 用 `-w 2 / 3600s`，否则 `-w 1 / 1800s`。公开版没有内部版
  opsec 的命令重写层，这里只把参数写进计划与提示词，不强制执行手工命令。

## 5. 运行期闸门

- **后台作业**：`job_start` 先取槽位，超过全局/单任务上限时排队（最长 10 分钟，
  超时返回可行动错误）。槽位在作业进程退出后释放；计划未启用时是空操作。
- **nice/timeout**：计划启用且 Linux 有 `nice` 时，作业以 `nice -n 10` 启动；
  有支持 `--foreground --kill-after` 的 GNU `timeout` 时，内层脚本套作业墙钟上限
  （计划启用时 6 小时）。超时仍能写回 rc，作业状态不会变成「无退出码」。
- **扫描限速**：`scan_with_nuclei` 自动加 `-rate-limit`；Bash 工具描述追加一段
  「资源自适应」建议（nuclei/ffuf/hashcat/john 参数），计划未启用时描述不变。
- **Go 运行时**：仅在计划生效时设置 `debug.SetMemoryLimit` 与 `runtime.GOMAXPROCS`；
  关闭时恢复进程启动值（Go 1.25+ 默认按 cgroup 配额算）与无上限堆。

## 6. API 与设置页

- `GET /api/resource`：轻量重探测容量，返回 `capacity`/`plan`/`settings`/`effective`。
- `PUT /api/resource`：部分更新；支持 `auto_tune`、`mode`、两个阈值、`auto_pause_scans`、
  `manual`。手工覆盖逐项校验范围，越界返回 400；`manual: {}` 清空全部覆盖。
- `POST /api/resource/retune`：重新探测并重算计划（设置页「重新探测」）。
- 设置页「执行与并发 → 资源自适应」卡片：容量/依据/警告、计划项、生效值、
  自动/手动、阈值、4 项手工覆盖、保存并应用、重新探测、一键应用推荐任务并发。
- 「一键应用推荐任务并发」会显式打开 `task_concurrency_enabled` 并写入推荐值；
  不会静默改动其他配置。

## 7. systemd / Docker

- `install.sh`（二进制部署）按物理内存 65%/80%、CPU 80% 写
  `MemoryHigh/MemoryMax/CPUQuota/TasksMax`，可用环境变量覆盖或关闭：

  ```bash
  sudo POJUN_MEM_HIGH=16G POJUN_MEM_MAX=24G POJUN_CPU_QUOTA=600% ./install.sh --mode=binary
  sudo POJUN_RESOURCE_LIMITS=0 ./install.sh --mode=binary   # 不加任何资源指令
  ```

  取值会归一：`16g`/`16GB` → `16G`，`6` → `600%`，`0/off` → 不写 TasksMax；
  非法格式直接报错，不把 systemd 会静默忽略的坏值写进 unit。
- 存量部署补 drop-in：

  ```bash
  sudo ./scripts/apply-systemd-limits.sh --dry-run
  sudo ./scripts/apply-systemd-limits.sh --mem-high 16G --mem-max 24G --cpu-quota 600%
  sudo ./scripts/apply-systemd-limits.sh --disable      # 删除本脚本生成的 drop-in
  ```

  脚本只写 drop-in 并打印后续 `daemon-reload`/`restart`，不自动重启。
- Docker：程序在容器内读 cgroup 配额缩放，**不改宿主**。compose 里的
  `mem_limit/mem_reservation/cpus/pids_limit` 是可选配额来源（默认注释），
  不设配额时会按宿主总量估算并提示「可能高估」。

## 8. 回滚

1. 设置页关闭「启用自动调优」并清空手工覆盖 → 立即回到默认行为（不限制作业、
   不缩放扫描、worker 回到显式值或 3）。
2. systemd 存量部署：`sudo ./scripts/apply-systemd-limits.sh --disable` 后
   `systemctl daemon-reload && systemctl restart pojun`。
3. 重新安装时 `POJUN_RESOURCE_LIMITS=0` 不写系统级资源指令。
4. 没有数据库迁移，也没有新增后台任务；关闭开关后 `resource_*` 设置键只是留存，
   不影响行为。

## 9. 已知边界

- 阈值与「临界暂停扫描/破解」当前只保存，不会主动暂停作业（与内部版一致，留待
  资源看门狗）。
- 公开版没有 opsec 命令重写层：hashcat/john/ffuf 的低负载参数通过提示词建议，
  不做命令级强制；`job_start` 闸门与 `scan_with_nuclei -rate-limit` 是强制的。
- 非 Linux 的内存/磁盘是保守估算，不能替代真实容量；容器内未设配额时同样可能高估。
- 计划每小时重算，扩容后最多 1 小时才反映到运行期；可在设置页点「重新探测」立即生效。
- worker/任务并发只对之后启动的任务生效，运行中的任务不重启。
