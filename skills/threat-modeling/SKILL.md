# 威胁建模（任务早期 · 轻量版）

> 目的不是产出漂亮文档，而是让 planner 在动手前回答三个问题：
> **系统是什么、哪里可能被滥用、先验证哪一条**。

## 1. 什么时候用

- 新任务/新资产域开始，只有域名、业务描述或一张架构图；
- 拿到一批 API/资产，不知道先测什么；
- 业务方给了一个功能清单（注册、支付、上传、邀请、后台、API）；
- 需要把“漏洞清单”升级成“攻击路径/滥用场景”；
- 复测前判断上一轮覆盖是否合理。

**不适用**：已有明确单一漏洞目标（直接走 `vuln-hunting`/`web-attack-methods`）；
纯资产发现（`attack-surface-recon`）；纯接口越权（`api-security-testing`）。

## 2. 四步法

### 第一步：系统与资产

用 `graph_overview` + 任务描述 + `list_assets` 填：

- 业务目标：谁用、解决什么问题、钱/数据/权限在哪；
- 资产：域名、IP、服务、API、后台、第三方依赖、云资源、移动端/小程序；
- 角色：匿名、普通用户、付费用户、商家、代理、管理员、内部员工、第三方；
- 数据：PII、支付、订单、凭证、日志、配置、模型/提示词；
- 信任边界：浏览器↔API、API↔DB、服务↔第三方、租户↔租户、用户↔管理员、
  开发/测试↔生产、Agent↔工具/外部内容。

### 第二步：滥用场景

不要只列“漏洞类型”，按“谁为了什么利益/破坏，利用哪条路径”写。四类：

| 类别 | 问题 | 例子 |
|---|---|---|
| 传统安全（STRIDE） | 伪造/篡改/否认/信息泄露/拒绝服务/提权 | 越权读订单、JWT 伪造、SSRF 打元数据 |
| 业务滥用 | 规则/流程/激励被批量利用 | 领券套利、退款欺诈、刷评、账号农场 |
| 供应链/依赖 | 第三方、CI/CD、制品、MCP/插件 | 依赖投毒、构建凭证、恶意 MCP 工具 |
| AI/Agent | 提示注入、工具越权、数据外泄、自动化滥用 | 间接提示注入、Agent 调用高权限工具、RAG 越权 |

每条滥用场景写：**角色 → 前置条件 → 路径/步骤（抽象） → 影响 → 可观测信号**。

### 第三步：优先级

用三个维度打分（1–5）：

- **影响**：资金/数据/权限/可用性/合规；
- **可能性**：前置条件是否容易满足（匿名可打 > 需登录 > 需内部权限）；
- **证据成本**：验证需要多少时间/资源（低=优先）。

优先级 ≈ 影响 × 可能性 ÷ 证据成本。优先做“高影响、低门槛、易验证”的场景；
对“高影响但难验证”的，先写 fact 标记假设，等资产/凭据到位再派意图。

### 第四步：转成意图

每条优先场景转成一条可执行意图（`add_intent`），summary 写：

```
验证 <角色> 能否在 <前置条件> 下，通过 <路径> 造成 <影响>；
成功判据：<可观测结果>；证据：<请求/响应/截图>；前置：<账号/环境/依赖>
```

不要把“测一下 XX”写成意图；要有成功判据和证据要求。

## 3. 输出模板（写进 `record_fact` 或任务摘要）

```markdown
## 系统
- 业务/用户/资产：
- 信任边界：
- 关键数据/资金/权限：

## 滥用场景（按优先级）
| # | 角色 | 场景 | 影响 | 可能性 | 证据成本 | 优先级 | 验证工具 |
|---|---|---|---|---|---|---|---|
| 1 | 匿名 | ... | 高 | 高 | 低 | P0 | http_request |

## 已排除/待确认
- 数据不足：
- 需要确认：
- 依赖第三方/环境限制：
```

## 4. 平台工具

| 目的 | 工具 |
|---|---|
| 看全局资产/图/覆盖 | `graph_overview`、`list_assets`、`list_untested_assets` |
| 补范围 | `add_task_scope`（补任务范围） |
| 记录假设/结论 | `record_fact`（负结果也写） |
| 派生验证意图 | `add_intent`（带成功判据/证据要求） |
| 查历史打法 | `kb_search`（业务欺诈/支付/API/云等） |
| 资产归属 | `attack-surface-recon` 的备案/证书/whois 方法 |

## 5. 常见错误

- 把“漏洞类型清单”当威胁模型：没有角色、路径、影响；
- 只列外部攻击，忽略内部/第三方/供应链/Agent；
- 不做信任边界：把“登录后”当成一个边界，实际还有租户/角色/服务间；
- 优先级只看影响，不看证据成本，导致任务卡在高成本方向；
- 把假设写成结论：未验证的场景只能写 fact（inferred），不能 report_finding。
